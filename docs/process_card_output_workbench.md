# Process Card Workbench production output (Task 06)

## Existing Task 01 flow

The pre-change flow is recorded in [process_card_output_existing_flow.md](process_card_output_existing_flow.md). Task 01's `save_output_checkpoint` remains the established ERPNext posting path: it writes positive production to native `Job Card Time Log.completed_qty`, which ERPNext aggregates into `Job Card.total_completed_qty`; the existing QCMC hook then synchronizes official totals to non-final Work Order operations.

## Workbench operational flow

The Process Card Workbench loads only the Job Cards explicitly linked through `Process Card.jobs`. It reads the linked cards' native Time Logs and filters rows by the explicit `qcmc_process_card` Link. Saving or correcting output locks the Process Card and Job Card, verifies Process Card write permission and Draft/In Progress status, confirms Job Card membership and matching Company/Workstation/valid submitted Work Order, validates the shift interval and Job Card precision, then saves through `Job Card.save()`.

Operational rows reuse the native `Job Card Time Log` child table and its `from_time`/`to_time` interval validation, but retain native `completed_qty = 0`. Hidden and read-only QCMC fields store Process Card, good quantity, rejected quantity, remarks, entry user/time, revision, and JSON correction history. A Job Card lifecycle guard rejects direct field edits, additions, and removals outside the audited Workbench APIs. This keeps operational checkpoint totals separate from ERPNext's official completed quantity. A retry with identical interval and values is idempotent; a different value requires the explicit Correct Entry action. Corrections require a nonblank reason and matching revision, append before/after values and actor/time to the row audit history, and never delete/reinsert the native row.

The Task 01 endpoint remains unchanged and available. It cannot overwrite a QCMC operational interval because its native completed-quantity semantics conflict with the existing employee-less row; the Workbench provides a separate explicit correction path over the same storage rows.

## Checkpoint schedule and quantities

`Shift Type.qcmc_checkpoint_interval_minutes` is a configurable integer, defaulting to 120 minutes. The Workbench generates slots from the Process Card's explicit shift start/end datetimes, including overnight shifts and a shorter final partial slot. Changing Shift Type configuration does not move existing entries: the Workbench retains entries at their stored interval and shows any interval no longer generated by the current schedule as historical. New entries must match a currently configured slot.

Good and rejected quantities use the Job Card's `for_quantity` field precision and stock UOM. They are stored separately: `good_qty` is accepted physical output; `rejected_qty` is rejected physical output; `recorded_qty` is their sum. The good target balance is `for_quantity - good_qty`, floored at zero. Workbench summaries group by production item and UOM and show official `total_completed_qty` separately. No quantities are converted or combined across different items/UOMs.

## Permissions and official posting boundary

The existing Process Card write permission and existing Company, Production Site, Workstation, Job Card, and Work Order checks govern entry. Output is available only in Draft or In Progress Process Cards. For Approval, Approved, and Cancelled cards are locked. No roles are added. The QCMC Job Card update hook skips progressive Work Order synchronization only when the request is explicitly saving operational checkpoint metadata; normal Task 01 output and existing Job Card updates retain the progressive synchronization behavior.

Operational saves do not set native `completed_qty`, submit/complete Job Cards, create Stock Entries, update Work Order manufactured quantities, or create payroll entries. Job Cards with sub-operations or native Time Log totals inconsistent with `total_completed_qty` are rejected so the operational save cannot silently recalculate official totals.

ERPNext's native Job Card validation still checks Workstation overlap and production capacity on these interval rows. Where native Workstation capacity rejects overlapping Job Card intervals, the Workbench reports the core validation error; this code does not bypass it. Multiple Job Cards can therefore record the same interval only when the Workstation's configured capacity and ERPNext validation allow the overlap.

## Dev-only schema synchronization

The implementation adds QCMC custom fields to ERPNext `Job Card Time Log` and HRMS `Shift Type`; no DocType is added. On a disposable development site only, apply the schema with:

```sh
bench --site <dev-site> migrate
bench --site <dev-site> clear-cache
```

No site migration or production change was run for this task.

## Later integration

The resulting good/rejected totals are operational records, not official production postings. A later controlled posting task must explicitly confirm and reconcile operational checkpoints before using Task 01's official `completed_qty` path or creating manufacture Stock Entries. Downtime and manpower remain separate future integrations.
